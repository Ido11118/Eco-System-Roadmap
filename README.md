# תוכנית עבודה ארגונית: Gantt & Work Plan Management

כלי Web פנימי לניהול תוכנית העבודה של הארגון. הכלי כולל גאנט אינטראקטיבי, טבלת תכולות, הרשאות לפי תחום, אבני דרך, ספרינטים, תמונות מצב (Snapshots) עם גרסאות, והשוואת תכנון מול ביצוע.

## הרצה מקומית

```bash
npx next dev -p 3001
```

ואז לפתוח בדפדפן את http://localhost:3001. לעצירה: `Ctrl+C`.

<details>
<summary>הכנה חד-פעמית (רק בפעם הראשונה על מחשב חדש)</summary>

דרישות: Node 22 ומעלה, ו-PostgreSQL 14 ומעלה שרץ על המחשב.

```bash
npm install
createdb workplan                              # יצירת בסיס נתונים מקומי
cp .env.example .env                           # ואז לערוך: DATABASE_URL, APP_URL=http://localhost:3001, SUPERUSER_EMAIL, SUPERUSER_PASSWORD
npm run db:migrate && npm run db:seed          # טבלאות, מבנה התחומים והצוותים, ו-Super User
npm run db:holidays                            # חגים ומועדים 2026–2027 בשורת "גורמים משפיעים"
npm run db:demo                                # אופציונלי: נתוני הדגמה
```

התחברות: עם `SUPERUSER_EMAIL` ו-`SUPERUSER_PASSWORD` שהוגדרו ב-`.env`.

## התחלה מהירה

### אפשרות א': Docker Compose (מומלץ לפריסה)

```bash
cat > .env <<'EOF'
DB_PASSWORD=סיסמה-חזקה-לבסיס-הנתונים
SUPERUSER_EMAIL=admin@your-org.example
SUPERUSER_PASSWORD=סיסמה-חזקה-למנהל
APP_URL=https://workplan.your-org.example
EOF
docker compose up -d --build
```

בכל עלייה של הקונטיינר מורצים: מיגרציות, אתחול מבנה התחומים והצוותים, ויצירת ה-Super User (רק אם עדיין לא קיים).

### אפשרות ב': הרצה ישירה (Node 22 + PostgreSQL 14 ומעלה)

```bash
npm ci
cp .env.example .env          # ולערוך את הערכים
npm run db:migrate            # יצירת הטבלאות
npm run db:seed               # תחומים, צוותים, שתי שורות לכל צוות, שורות רוחביות, Super User
npm run build && npm start    # http://localhost:3000
```

לפיתוח: `npm run dev`. להוספת נתוני הדגמה לבסיס נתונים ריק: `npm run db:demo`.

## מודל הרשאות

| | צפייה | עריכת תחום | עריכה רוחבית | Snapshots (יצירה ועריכה) | ניהול משתמשים |
|---|---|---|---|---|---|
| ממתין, נדחה, מושעה | ✗ (גם ב-API) | ✗ | ✗ | ✗ | ✗ |
| משתמש מאושר | ✓ הכל | רק תחומים שהוקצו לו | רק עם הרשאה רוחבית | ✗ | ✗ |
| Super User | ✓ | ✓ | ✓ | ✓ | ✓ |

- ההרשאות נאכפות בשרת בכל פעולה (`src/server/plan.ts`), גם בהעברת תכולה בין שורות או צוותים. הסתרת כפתורים בממשק היא נוחות בלבד.
- בקשת התחומים בהרשמה נשמרת בנפרד (`user_approval_requests`) מההרשאות שניתנו בפועל (`user_domain_permissions`).
- רק Super User אחד: נאכף באינדקס ייחודי חלקי בבסיס הנתונים. הוא נוצר מתוך משתני סביבה ואין פרטי גישה בקוד.
- השעיה או דחייה של משתמש מנתקות מיד את כל הסשנים שלו.
- הגנות נוספות: בדיקת Origin בבקשות משנות (CSRF), הגבלת קצב בהתחברות (סופרים רק ניסיונות כושלים, לפי חשבון וכתובת), הרשמה ושחזור סיסמה, וכותרות אבטחה (CSP, X-Frame-Options ועוד). מאחורי Reverse Proxy יש להגדיר `TRUST_PROXY=true` כדי שההגבלה תהיה לפי כתובת הלקוח.
- `APP_URL` חייב להיות הכתובת הציבורית המדויקת (כולל https). בדיקת ה-CSRF מקבלת בקשות שמקורן בכתובת זו, גם כשה-Reverse Proxy משנה את כותרת Host.
- סשנים וקישורי איפוס שפג תוקפם נמחקים אוטומטית. ברשימת המשתמשים שנשלחת לממשק מופיעים רק משתמשים שאושרו (ממתינים ונדחים לא נחשפים).
- קישור איפוס סיסמה הוא חד-פעמי גם בבקשות מקבילות.
- אם בעת האתחול כבר קיים חשבון עם כתובת ה-Super User (למשל מישהו נרשם איתה מראש), כל הסשנים, ההרשאות והבקשות שלו מבוטלים לפני שהוא מקודם.

## החלטות עיקריות

**שבועות.** שבוע הוא ראשון עד שבת, ומזוהה לפי תאריך יום ראשון שלו (עמודת `DATE`). שבוע משויך לחודש ולשנה של יום ראשון שלו. מספר השבוע הוא סידורי בתוך השנה: שבוע 1 הוא השבוע שיום ראשון שלו הוא יום הראשון הראשון בשנה. "השבוע הנוכחי" מחושב לפי Asia/Jerusalem. כל החישובים נעשים על תאריכים קלנדריים בלי שעות, ולכן אינם מושפעים משעון קיץ.

**חפיפות.** בשורת צוות אסור ששתי תכולות יחפפו. הכלל נאכף בשלוש שכבות: בממשק לצורך משוב מיידי, בשרת עם נעילת שורה (`SELECT … FOR UPDATE`), ובבסיס הנתונים עצמו עם Exclusion Constraint (`btree_gist`), כך שגם סקריפט או נקודת קצה עתידית לא יכולים ליצור חפיפה. בשורות הרוחביות (גורמים משפיעים, מופעים רוחביים) חפיפה מותרת, והתכולות מוצגות בנתיבים זו מתחת לזו.

**עריכה מקבילה.** לכל ישות יש עמודת `version`. עדכון או מחיקה עם גרסה ישנה נדחים בתשובה 409, והממשק מציג הודעה ומרענן את הנתונים. הנתונים מסונכרנים עם השרת כל 10 שניות וגם בחזרה לחלון. בזמן שמירה הסנכרון מושהה, ותשובת רענון שהגיעה באיחור לעולם לא מחזירה ישות לגרסה ישנה יותר. עדכון מרובה נועל שורות בסדר קבוע כדי למנוע Deadlock.

**מחיקה ו-Undo.** תכולות, שורות, אבני דרך וספרינטים נמחקים ב-Soft Delete. אחרי כל מחיקה ואחרי הזזת תכולה מוצגת הודעה עם כפתור "ביטול", וגם `Ctrl+Z` מבטל את הפעולה האחרונה. שחזור שורה מחזיר רק את התכולות שנמחקו יחד איתה.

**Snapshots.** Snapshot הוא עותק JSON מלא של התוכנית: תכולות עם המזהים המקוריים, שורות וסדרן, אבני דרך, ספרינטים, מידע רוחבי ומבנה התחומים. הוא נוצר בטרנזקציית `REPEATABLE READ` ולכן עקבי. בכל שמירת גרסה השרת מאמת את התוכן לפי אותם כללים של התוכנית החיה: אין מזהים כפולים, מזהה חיובי חייב להיות מזהה שכבר הופיע ב-Snapshot (ישות חדשה נשלחת עם מזהה שלילי), שיוכי צוות תקינים, ואין חפיפות. מבנה התחומים והמשתמשים נלקח מהגרסה הקיימת ולא מהלקוח. כל עריכה של ה-Super User יוצרת Revision חדש, והגרסאות הישנות לעולם אינן משתנות. שחזור גרסה יוצר Revision נוסף עם התוכן הישן. ההשוואה משתמשת בגרסה הנוכחית אלא אם נבחרה גרסה אחרת. תכולה שנוספה בעריכת Snapshot מקבלת מזהה מאותו רצף של התוכנית החיה, כדי שלא תתנגש בהשוואה.

**Audit Log ו-Snapshots הם שני מנגנונים נפרדים.** `audit_logs` מתעד כל פעולה: מי ביצע, מתי, ומה השתנה. את ההיסטוריה של תכולה רואים בחלונית הפרטים שלה, ואת היומן המלא רואים במסך הניהול.

## תכנון מול ביצוע

הלוגיקה נמצאת ב-`src/lib/compare.ts` ומכוסה בבדיקות יחידה.

1. **התאמה לפי ID בלבד.** שינוי שם, זמן, שורה או צוות לא שובר את ההתאמה.
2. **סיווג.** לכל תכולה שקיימת בשני המצבים יש בדיוק סיווג זמן אחד: ללא שינוי, נדחה או הוקדם. הקובע הוא מועד הסיום, ואם הוא זהה, מועד ההתחלה. תגיות אפשריות: ללא שינוי, נדחה, הוקדם, התארך, התקצר, בוטל (סטטוס), נמחק (קיים רק ב-Snapshot), נוסף, הושלם, לא הושלם, הושלם ולא תוכנן, הועבר צוות, שם שונה. "נמחק" ו"בוטל" הם מצבים נפרדים. תכולות שנמחקו מוצגות עם סימון, ולא מוסתרות.
3. **פריסת שורות וירטואליות.**
   - כל ID הוא יחידת תצוגה אחת. התכנון והביצוע שלו מצוירים תמיד באותה שורה וירטואלית.
   - התפוסה של כל ID מחושבת כאיחוד המקטעים בפועל, ולא כטווח מינימום עד מקסימום. כך הרווח בין תכנון לביצוע שאינם רציפים נשאר זמין לתכולה אחרת.
   - בתוך כל שורה מקורית מתבצעת הקצאה חמדנית לפי זמן התחלה (First-Fit). שורה וירטואלית נוספת נפתחת רק כשיש חפיפה בין IDs שונים.
   - התכולות נשארות בקבוצת השורה המקורית שלהן, ולכן הסדר יציב.
   - השורות הווירטואליות קיימות רק בתצוגה. בסיס הנתונים לא משתנה.
4. **סיכום ניהולי, בלי ספירה כפולה.**
   - תוכננו = הושלמו + לא הושלמו + בוטלו + נמחקו. החלוקה הזו מתבססת על תכולות ה-Snapshot בלבד.
   - "נדחו" ו"הוקדמו" הם מדדי זמן נפרדים.
   - "נוספו" לא נכללות באחוז ההשלמה.
   - המדדים מחושבים על תכולות צוות בלבד, ויש גם פירוק לפי תחום.

## שינוי מבנה התחומים והצוותים

- **צוותים:** מנוהלים במסך **ניהול מערכת ← מבנה הגאנט** (מנהל המערכת בלבד): שינוי שם, הוספת צוות לתחום והסרת צוות. הסרה מעבירה את הצוות לארכיון ומוחקת (מחיקה רכה) את התכולות, השורות ואבני הדרך שלו, אחרי אישור ועם אפשרות לצפות בהם קודם. לתחום חייב להישאר לפחות צוות אחד. ההרשאות לפי תחום, ולכן שינויי צוותים לא משנים הרשאות.
- **התקנה ראשונה:** הצוותים נוצרים מ-`src/lib/org.ts`. אחר כך בסיס הנתונים הוא מקור האמת, ו-`db:seed` (שרץ בכל עלייה) לא דורס אותם.
- **תחומים:** קבועים ב-`src/lib/org.ts` (שם וסדר מתעדכנים ב-`db:seed`). **אסור לשנות מזהה (`id`) קיים**, כי כל הקשרים במסד הנתונים מבוססים עליו ולא על שמות.

## תפעול

- **בדיקת תקינות:** `GET /api/health` מחזיר 200 כשהשרת ובסיס הנתונים זמינים (503 אחרת). ה-Dockerfile משתמש בה כ-HEALTHCHECK.
- **חגים:** `npm run db:holidays` מוסיף את חגי ישראל 2026–2027 לשורת "גורמים משפיעים" (בטוח להרצה חוזרת — חג קיים לא נוסף שוב). התאריכים חושבו מהלוח העברי.
- **סטטוסים ותיעדוף:** מוגדרים במסך ניהול מערכת ← הגדרות (שם, צבע, משמעות, סדר). "מחיקה" היא ארכוב — תמונות מצב ישנות ממשיכות להציג את הערך המקורי.
- **העברת ההגדרות לפרודקשן:** בפיתוח, כל שינוי במסך ההגדרות נכתב אוטומטית לקובץ `config/catalog.json`. דוחפים אותו לגיט, ובעליית השרת (`db:seed`) ההגדרות מוחלות — רק אם הקובץ השתנה מאז ההחלה הקודמת. מחיקה עם העברה (למשל "ממתין" ← "בביצוע") מעבירה גם את התכולות בפרודקשן. שינויים שנעשו ישירות בפרודקשן נשמרים כל עוד הקובץ לא משתנה. ייצוא ידני: `npm run catalog:export`.
- **גיבוי:** `pg_dump` לבסיס הנתונים. כל המידע, כולל ה-Snapshots, נמצא בו.
- **קובצי סביבה:** כל המשתנים מתועדים ב-`.env.example`. הקובץ `.env` מוחרג מגיט ומה-Docker image (`.gitignore`, `.dockerignore`).
- **שחזור סיסמה:** כש-SMTP מוגדר, נשלח קישור במייל. בלי SMTP, ה-Super User מפיק קישור איפוס חד-פעמי ממסך ניהול המשתמשים ("קישור לאיפוס סיסמה"). בייצור הקישור עצמו לא נכתב ללוג, אלא אם הוגדר `LOG_RESET_LINKS=true`.
- **החלפת סיסמת ה-Super User:** דרך "שכחתי סיסמה" או קישור איפוס. ה-seed לא משנה Super User קיים.
- **מיגרציות חדשות:** לעדכן את `src/db/schema.ts`, להריץ `npm run db:generate` ואחר כך `npm run db:migrate`.
